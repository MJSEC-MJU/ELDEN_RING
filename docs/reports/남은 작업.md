## 1. 필수 — Phase 1을 실제로 동작시키려면 막혀 있는 것

### ① ModSecurity audit log shipper 미연결

**현상**
- 컨트롤러의 `POST /api/v1/modsec-events` 엔드포인트는 인증·정규화·파이프라인까지 정상 동작.
- 하지만 NGINX Ingress Controller가 stdout으로 뱉는 ModSecurity audit log를 그 엔드포인트로 밀어주는 컴포넌트가 **없음**.
- 결과: 현재 WAF가 SQLi/XSS/Path Traversal을 차단해도 Phase 1은 그 사실을 모름. 시연은 `/api/v1/events/manual` 또는 Falco 경로로만 가능.

**근거**
- `docs/phase1/development-plan.md` §3.3에서 두 방식(Fluent Bit sidecar / K8s API 로그 tail) **검토만** 되어 있고 결정·구현 없음.
- `services/runtime-defense/src/main.py:151` 의 docstring "Receive ModSecurity audit log (from Fluent Bit or log collector)" — 수신 측만 만들어진 상태.
- `kubernetes/` 어디에도 Fluent Bit sidecar / log streamer 매니페스트 없음 (검색 결과 0건).

**해결 방안 (둘 중 택 1)**
- (A) Fluent Bit sidecar를 ingress-nginx Pod에 추가 — `tail` 입력 + `http` 출력으로 컨트롤러에 POST. 토큰은 `Authorization` 헤더로 동봉.
- (B) Phase 1 컨트롤러가 K8s API로 ingress-nginx Pod 로그를 직접 stream — 별도 sidecar 불필요, 대신 컨트롤러에 `pods/log` watch 권한 추가 필요.

**작업 범위**
- 매니페스트 1~2개 (Fluent Bit ConfigMap + sidecar patch, 또는 컨트롤러 RoleBinding 확장 + 코드 모듈)
- E2E 테스트 갱신: WAF 차단부터 Phase 2 큐 발행까지 한 번에 검증

### ② H-001: Falco Sidekick `customheaders` 미적용

**현상**
- `kubernetes/security/falco/values.yaml:103-105`의 falcosidekick은
  `address: http://runtime-defense-controller.elden-production:8080/api/v1/falco-events` 까지만 설정됨.
- Bearer 토큰 헤더 **없음**.
- 현재 dev에선 `WEBHOOK_AUTH_TOKEN`이 빈 placeholder라 인증 비활성 모드 → 통신 무사.
- **프로덕션에서 토큰을 실제 값으로 회전하는 순간 Falco 이벤트가 401로 전부 짤린다.**

**해결 방안** (`docs/phase1/cross-team-handoffs.md` H-001에 명시됨)
```yaml
falcosidekick:
  config:
    webhook:
      address: "http://runtime-defense-controller.elden-production:8080/api/v1/falco-events"
      customheaders: "Authorization:Bearer <RUNTIME_DEFENSE_WEBHOOK_TOKEN>"
```

**회전 시점 동기화 절차** (cross-team-handoffs H-001 인용)
1. `kubectl create secret generic runtime-defense-secrets --from-literal=webhook-auth-token=<NEW>` (`elden-production`)
2. `kubernetes/security/falco/values.yaml`의 `customheaders` 값 갱신
3. `helm upgrade falco falcosecurity/falco -n falco -f .../values.yaml`
4. `kubectl rollout restart deployment/runtime-defense-controller -n elden-production`

**우선순위 분기**
- dev / kind: Low (토큰 비활성)
- staging: Medium
- production: **High** (토큰 회전 시점에 필수)

### ③ H-002: trace_id Phase 2/3/4 전파 미합의

**현상**
- Phase 1은 `run_pipeline` 진입 시 12자리 hex `trace_id`를 발급해
  - 모든 로그 라인에 `trace_id` 필드로 노출 (구조화 로깅)
  - Redis 컨텍스트의 `metadata.trace_id`에 포함
- Phase 2/3/4는 수신만 할 뿐, 자기 로그·하류 메시지에 propagate하지 않음.
- 결과: 단일 trace_id로 Phase 1→2→3→4 사고 RCA 불가.

**해결 방안** (`docs/phase1/cross-team-handoffs.md` H-002에 명시됨)
- 각 Phase가 수신 컨텍스트의 `metadata.trace_id`를:
  1. 자기 Phase 모든 로그 라인에 동일 필드로 포함 (structlog `bind` 또는 `LoggerAdapter`)
  2. 다음 Phase로 보내는 메시지에 그대로 propagate
- additive 변경이라 미적용 시에도 동작 영향 없음(필드 누락 시 빈 문자열 fallback).

**우선순위**
- 즉시 적용: Low
- 운영 사고 시 추적성: Medium (사고 RCA 가속을 위해 합의 권장)

## 2. 권장 — 시연은 되지만 운영에서 곧 문제

### ④ 영구 저장소 없음 (인메모리 상태 유실)

**현상**
- 다음 상태가 모두 컨트롤러 프로세스 메모리에만 존재:
  - `events_store`, `contexts_store`, `failed_logs` (`src/main.py`)
  - `DefenseManager._blocked_ips`, `_disabled_endpoints`, `ip_attack_count`, `endpoint_attack_count`, `action_history` (`src/defense/manager.py`)
- **Pod 재시작 / 롤링 / HPA 스케일다운 → 누적 카운트·차단 set 유실**
- 영향:
  - 차단했던 IP가 다시 `IP_BLOCK_THRESHOLD=3`회 채울 때까지 통과
  - 비활성화한 엔드포인트도 마찬가지로 5회 다시 누적될 때까지 503 대신 정상 응답
  - `/api/v1/contexts/latest`, `/api/v1/defense/actions` 같은 시연용 조회는 빈 리스트로 시작
- 단, 능동 방어 자체(Istio CR)는 K8s API에 영구 저장됨 → "차단" 효과는 살아있음. 다만 컨트롤러는 그 사실을 모르고 새로 만들려다 409 를 받을 수 있음.

**개발 계획서**: PostgreSQL은 "추후"로 미뤄짐 (인프라에 PG 미구성).

**해결 방안 (선택지)**
- (A) Redis 자체에 카운트/차단 set 저장 — Phase 1이 이미 Redis 의존하므로 추가 인프라 0
- (B) PostgreSQL 도입 — 인프라 신설 필요
- (C) `DefenseManager`가 시작 시 K8s API에서 기존 `AuthorizationPolicy`/`VirtualService`를 조회해 set을 복원

→ 단기적으로는 (A)가 가장 가벼움. (C)는 K8s를 단일 진실로 두는 깔끔한 접근이지만 카운트는 별도로 다뤄야 함.

### ⑤ 시크릿 회전 + ExternalSecrets / SealedSecrets 도입

**현상**
- `kubernetes/environments/production/runtime-defense-secret.yaml:29` —
  `webhook-auth-token: "elden-ring-dev-CHANGE_ME_IN_PROD"` 가 그대로 git에 커밋됨.
- cross-team-handoffs.md에 "토큰이 두 곳(K8s Secret + Falco Helm values)에서 분리 관리되는 점은 향후 ExternalSecrets 또는 SealedSecrets 도입 시 일원화 검토" 메모만 있음.

**해결 방안**
- (A) 단기: 프로덕션 진입 전 `openssl rand -hex 32` 토큰 생성 → 매니페스트 stringData를 비우거나 `kubectl create secret`으로 클러스터 내 직접 생성, git에는 placeholder 유지.
- (B) 중기: ExternalSecrets Operator + 시크릿 매니저(Vault / AWS Secrets Manager / GCP Secret Manager) 연동 — Falco values 와 컨트롤러 Secret 양쪽이 같은 외부 소스를 참조하도록 일원화.

### ⑥ Source mapper 정적 ConfigMap (수동 갱신)

**현상**
- `kubernetes/environments/production/route-map-configmap.yaml`에 3개 엔드포인트 하드코딩 (POST /api/login, GET /api/search, GET /api/file).
- target-app에 새 엔드포인트가 추가되면 매번 사람이 손으로 ConfigMap 업데이트 + line_start/line_end도 직접 채워야 함.
- 개발 계획서 §5: "수동 작성 ConfigMap (MVP) — target-app이 3개 엔드포인트뿐이라 AST 파서 불필요. 확장 시 파서 추가 가능".

**해결 방안 (필요 시)**
- AST 기반 자동 생성 스크립트: `target-app/app.py`를 `ast.parse`로 훑어 `@app.route` 데코레이터·함수명·라인 추출 → routes.json 빌드 시 자동 생성.
- 또는 OpenAPI/Swagger 스키마에서 추출.

→ target-app이 시연 수준에 머무는 한 우선순위 낮음.

### ⑦ WAF false positive 예외 처리 운영 절차 부재

**현상**
- ModSecurity가 정상 트래픽을 차단할 때의 진단법은 `docs/phase1/troubleshooting.md` §4 에 적혀 있음 (rule id 확인, paranoia level 조정 권고).
- 그러나 **실제 예외 룰을 어디에 적을지** — `kubernetes/service-mesh/ingress/configmap.yaml`의 `modsecurity-snippet` 안인지, `target-app-ingress.yaml`의 annotation `modsecurity-snippet`인지, 별도 파일인지 — 절차로 정의되지 않음.

**해결 방안**
- 운영 절차 문서화:
  1. 차단 룰 ID 확인 (`troubleshooting.md` §4 명령)
  2. 룰 예외 위치 결정 (전역 ConfigMap = 모든 Ingress / target-app annotation = 단일 Ingress)
  3. `SecRuleRemoveById <RULE_ID>` 또는 `SecRuleUpdateTargetById` 추가
  4. `kubectl rollout restart deployment ingress-nginx-controller -n ingress-nginx`
- troubleshooting.md §4 말미에 위 4단계를 절차로 추가.

## 3. 우선순위 추천 작업 순서
